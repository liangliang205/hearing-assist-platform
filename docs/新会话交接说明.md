## 2. 最重要的决策（不要再走回头路）

### 2.1 架构：桌面端为主，而不是 Web

浏览器拿不到系统音频、不能常驻，产品价值无法实现。详见 `docs/项目需求文档_v2.0_桌面端优先.md` §1。

### 2.2 系统级音频：放弃自研 APO，改用「虚拟声卡 + WASAPI 路由」

**已验证结论（2026-11-06）**：APO 路线在 Windows 11 25H2（build 26200）上跑不通，已彻底放弃。

踩过的坑（不要重试）：

- 注册路径必须是 `HKCR\AudioEngine\AudioProcessingObjects\{CLSID}`，不是 `HKLM\...\CurrentVersion\AudioEngine`
- 端点插槽用 `{d04e05a6-…},1`(LFx) / `,5`(SFx) / `,7`(EFx)
- Win11 引擎会 **QueryInterface `IAudioSystemEffects3`**（`{C58B31CD-...}`），只实现 `IAudioSystemEffects` 会被拒
- `MMDevices\...\Render\{guid}` 键受系统保护，需 `SeTakeOwnershipPrivilege` 才能写
- 补全以上后：引擎**创建对象成功，但一个方法都不调用**就丢弃（已用全方法埋点证实：11 个方法调用次数全为 0）
- 测试开关 `DisableProtectedAudioDG=1`、版本资源、效果名称/关联值、重启——全部试过，无效

**结论：问题在"如何挂进 Win11 25H2 的端点效果链"，不是我们的代码。生态里没人走这条路。**

### 2.3 采用的方案（有生态验证）

研究过三个项目，全部用虚拟声卡：

| 项目 | 做法 |
|---|---|
| [lyhxx/panda](https://github.com/lyhxx/panda) | VB-CABLE 做虚拟麦克风 |
| [RVC-WebUI](https://github.com/RVC-Project/Retrieval-based-Voice-Conversion-WebUI) | 实时变声，端到端 170ms / ASIO 90ms |
| [RvcStudio](https://github.com/3egirlsdream/RvcStudio) | WASAPI 路由 + 安装器集成 VB-CABLE + 延迟监控 |

**我们的输出侧路由**（反过来用）：

```
所有应用 → 系统默认播放设备 = CABLE Input
                ↓
        引擎捕获 CABLE Output
                ↓
        Rust DSP（增益 + 后续频率重映射）
                ↓
          真实耳机/音箱
```

用户只改一次「默认播放设备」，程序可自动切换与还原——**满足"不需要逐应用配置"的需求**。

### 3.4 默认设备接管与还原 `rust/hearlink-audio/src/routing.rs`（任务 2 已完成）

安全规则：**宁可没接管成功，也不能让用户"电脑突然没声音"**。所以顺序固定为
「先落盘状态 → 再切设备」，任何一步失败都立刻回滚。

- 状态文件：`%APPDATA%\HearLink\routing.json`（先写 `.tmp` 再 rename，避免半截 JSON）
- `Takeover` 是 RAII：正常返回 / `?` 提前返回 / panic 都会在 `Drop` 里还原
- 被强杀时 `Drop` 不会跑 → 下次启动 `recover()` 看到 `pending: true` 且原 pid 已退出就先还原
- `restore` 命令：手动还原；原引擎进程还活着时**拒绝动手**（避免抢走正在用的设备），`--force` 才强制
- 还原时若记录里的设备已被拔掉，跳过并告警，不会卡死在"永远还原不了"
- `run --takeover <名字|端点ID>`：接管 + 运行 + 退出还原；`--seconds 0` 表示一直跑到 Ctrl+C
- 回环保护：接管目标是输出设备本身时直接报错退出（否则系统声音会灌回自己）

已实测（2026-11-06，开发机）：

| 场景 | 结果 |
|---|---|
| `run --takeover "CABLE Input" --seconds 6` | 切到 CABLE Input → 运行 → 退出时自动还原，exit 0，状态文件已删 |
| 强杀引擎（`Stop-Process -Force`） | 默认设备停在 CABLE Input、状态文件 `pending: true`、pid 已退出（符合预期） |
| 强杀后再 `run`（不带 takeover） | 启动即打印"检测到上次异常退出遗留的设备接管，已还原"，默认回到扬声器 |
| 强杀后 `restore` | 还原成功、状态文件删除；再执行一次报"没有需要还原的设备接管" |
| 引擎运行中执行 `restore` | 拒绝并提示"正被另一个引擎进程接管中，未做改动" |
| `--takeover` 与 `--output` 同一设备 | 报错退出，未切换任何设备 |
| `cargo test` | 15/15（7 个名称匹配 + 4 个状态文件/pid + 4 个 biquad） |

**未实测**：Ctrl+C / 关闭控制台窗口的还原路径。已注册 `SetConsoleCtrlHandler`（置位
`SHUTDOWN`，主循环看到后有序收尾并还原），但当前这台机器上无法给后台无窗口进程投递
console control event（`taskkill` 不带 `/F` 报 "can only be terminated forcefully"），
所以只做了代码审查。**即使该路径失效，也有状态文件兜底**：下次启动/`restore` 即恢复。

### 3.5 配置热更新 `rust/hearlink-audio/src/hotswap.rs`（任务 3 已完成）

目标「换档案/重算补偿后 1 秒内生效，不用重启引擎」。

- watcher 普通线程每 300 ms 看一次 `--profile` 文件指纹（mtime + 长度），变了就重建滤波器链
- 通过无锁 `ArrayQueue` 交给音频回调；**回调里只 `pop` + `Option::replace`，不加锁、不分配**
- 旧链不回调里析构，推进 `retired` 队列由 watcher 线程释放 —— 不让 malloc/free 进实时线程
- 写了一半的 JSON（桌面端正写到一半）解析失败：保留上一份配置、300 ms 后重试，报错只提示一次
- `--no-watch` 可关掉；每秒统计行带 `配置 vN`，`N` 是**音频回调实际应用**的次数，不信 watcher 的一面之词
- 建议桌面端用「临时文件 + rename」原子写 `profile.json`（仓库里 `routing.rs` 的 `save` 就是这么做的）

已实测（2026-11-06）：

| 场景 | 结果 |
|---|---|
| 引擎运行中改 `hot-test-profile.json`（LEFT 500 Hz 5→15 dB） | 1 秒内打印"配置已热更新：左 2 段 / 右 1 段"，随后统计行从 `配置 v0` 变 `配置 v1` |
| 热更新期间数据链路 | 入/出帧数连续、丢弃 0、欠载 96（与更新前一致），无错误 |
| `--no-watch` | 不打印"监听配置变化"，运行正常，exit 0 |
| `cargo test` | 19/19（新增 4 个：换链+退役、空轮询、指纹变化、坏 JSON 后恢复） |

### 3.7 频率重映射 `rust/hearlink-audio/src/lowering.rs`（任务 5 已完成）

方案二的算法：**band shift**（STFT 分段搬移），与增益补偿共用同一条处理管线
（`Pipeline` = EQ → lowering → 限幅），热更新时整体替换。

- 1024 点 FFT、sqrt-Hann 窗、50% 重叠、完美重叠相加；额外延迟一个帧长（≈21 ms）
- 把 `[fmin, fmax]` 的复数 bin 整体下移 `shiftHz`，**同时搬共轭镜像**（否则输出不是实信号、幅度只剩一半）
- 相邻帧在目标频率上有 π 相位差（搬移量为奇数 bin 时会互相抵消）→ 每帧乘 ±1 修正
- 原频段保留、只叠加副本（-3 dB），避免把用户残余听力频段挖掉；链路末端限幅 ±1
- 参数来自 profile 的 `frequencyLowering`：`enabled` / `shiftHz`（可空，空则取半个带宽）/ `fmin` / `fmax`
- **两个方案互斥**：`enabled: true` 时管线只做搬移，**不再叠加** EQ 增益补偿（用户要求：只需要生效一个）；
  引擎启动与热更新日志都会打印当前方案（`处理方案：频率重映射 …（增益补偿不叠加）` / `处理方案：增益补偿 …`）
- 桌面端：「原音/增强」开关同时作用于系统全局——选「原音」时引擎直通（`profile.bypass = true`，不做任何处理，
  方便 A/B 对比），选「增强」时按当前方案处理，1 秒内热更新
- 桌面端：「增强方案」里直接选方案二即启用（原来 ③ 卡片里的独立开关已并入这里，避免两处控制打架）；
  ③ 卡片只显示当前方案与总开关。选完写 `profile.json`，引擎运行中 **1 秒内热更新**
- 新增离线自测命令 `lowering-test`，与 `selftest` 并列

已实测（2026-11-06，48 kHz）：

| 场景 | 结果 |
|---|---|
| `lowering-test --tone 6000`（fmin 4000 / fmax 8000 / 搬移 2000 Hz） | 6000 Hz 原信号 0.2000（0 dB）；**3984 Hz 出现 0.1400（−3.1 dB）**；1000 Hz 底噪 −81 dB |
| 单元测试（26/26） | 含"整数 bin 测试音被正确搬移"、"奇数 bin 搬移不互相抵消"、"参数非法时拒绝"、**"开了搬移就不再叠加 +12 dB 增益"**、"关掉搬移时增益照常生效" |
| 实时链路（启用搬移，release） | 回调平均 **41 µs / 最大 96 µs**（预算 5333 µs），欠载 96 帧、丢弃 0 |
| 实时链路（debug） | 回调平均 640 µs / 最大 1.7 ms，仍远低于预算 |
| 运行中把 profile 换成启用搬移的版本 | 打印"配置已热更新…频率重映射 4000–8000 Hz 下移 2000 Hz"，统计行变 `配置 v1`，无欠载/丢弃新增 |
