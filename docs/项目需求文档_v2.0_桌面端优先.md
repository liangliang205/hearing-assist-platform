## 1. 背景：为什么 Web 形态走不通

v0.1 已经跑通「测听 → 生成补偿配置 → 浏览器内 AB 预览」，验证了核心算法与交互。但它有三个绕不过去的硬约束：

| 约束 | 具体表现 | 影响 |
| --- | --- | --- |
| **浏览器无法接管系统音频** | Web Audio 只能处理页面内的音频节点，碰不到其他程序的输出 | 产品的核心价值（让电脑所有声音都经过处理）完全无法实现 |
| **音频必须留在本机** | 听障用户的听力曲线属于敏感健康数据，原始音频更不该上传 | 云端处理路线在合规与信任上都不可行 |
| **浏览器不能常驻** | 关掉标签页就失效，无法开机自启、无法后台运行 | 无法成为"日常使用的工具" |

结论：**桌面端是产品的必然形态，不是技术偏好**。Web 版保留两个用途：开发期浏览器预览、答辩演示。

## 2. 产品定位

### 2.1 一句话

> 给听障用户一个装在自己电脑上的"声音翻译器"：测一次听力，之后电脑里所有声音都按你的听力曲线调整后播放。

### 2.2 目标用户

| 用户 | 特征 | 核心诉求 |
| --- | --- | --- |
| 主要用户：轻中度听障者 | 有残余听力，未配或不便配助听器，日常用 PC 办公/看视频/开会 | 听得清、不用戴助听器、操作简单 |
| 次要用户：重度听障者 | 高频损失严重，语音识别困难 | 至少能看清字幕 |
| 潜在用户：听力正常但需要特定场景增强 | 如嘈杂环境、老年性听力下降早期 | 临时增强 |

### 2.3 与助听器的关系

**不是替代品，是软件侧补充**。定位为「辅助聆听工具」，不做医疗诊断、不做临床验配。所有界面对此必须有明确说明。

## 4. 业务需求

### 4.1 M1 桌面应用骨架与本地数据

**目标**：一个能装、能离线用、数据不出本机的 Windows 应用。

| 功能点 | 说明 |
| --- | --- |
| 安装包 | Windows x64 安装包，双击安装，无需管理员权限（尽量） |
| 离线可用 | 断网状态下，测听、档案、本地音频增强全部可用 |
| 本地存储 | SQLite 单文件，存于用户数据目录（`%APPDATA%\HearLink\hearlink.db`） |
| 数据导出/删除 | 设置页提供「导出全部数据」「清空全部数据」 |
| 开机自启 | 可选开关（默认关闭） |
| 托盘常驻 | 关闭窗口可最小化到托盘（为虚拟声卡做准备） |

**验收标准**
- 断网安装后能完成一次完整测听并生成档案；
- 卸载后本地数据可保留或删除（由用户选择）；
- 数据库文件可被用户找到并备份。

### 4.2 M2 听力自测（左右耳独立）

**目标**：3–5 分钟内测出左右耳各自的听力曲线。

| 功能点 | 说明 |
| --- | --- |
| 耳别独立 | 左耳、右耳各自独立会话、独立结果，互不影响 |
| 频点 | 250 / 500 / 1000 / 2000 / 4000 / 8000 Hz（可扩展到 125、3000、6000） |
| 流程 | 自适应阶梯法：40 dB HL 起，听到降 10 dB，未听到升 5 dB，形成 5 dB 包夹即终止 |
| 防误操作 | 播放中禁止作答；可重听；可中止 |
| 结果展示 | 双耳听力图（右耳红圈 / 左耳蓝方）、逐耳 PTA、WHO 2021 分级 |
| 通俗说明 | 用非专业语言解释"你在哪个频段听不清、这会影响什么"（如"高频损失，听女声和辅音吃力"） |
| 测听范围选择 | 双耳依次 / 仅左耳 / 仅右耳 |

**验收标准**
- 同一用户重复测听，两次 PTA 差异 ≤ 10 dB（同一设备同一环境）；
- 左右耳结果独立存储，单侧未测听时另一侧不受影响；
- 生成的说明文案与分级一致，不含诊断性表述。

**已知限制（必须在界面声明）**
- 浏览器/桌面端无法做声学校准（dB SPL），结果为**相对听阈**；
- 耳机差异会显著影响结果，需记录设备备注。

### 4.3 M3 听力档案管理

| 功能点 | 说明 |
| --- | --- |
| 多档案 | 一个用户可以保存多份档案（如"我的耳机""客厅音箱""旧档案"） |
| 档案内容 | 左右耳曲线、PTA、分级、补偿参数、生成时间、设备备注 |
| 切换与重命名 | 主界面可切换当前生效档案 |
| 删除 | 支持删除单份档案 |

**验收标准**：切换档案后，增强模块立即使用新参数。

### 4.4 M4 听力增强（增益补偿，方案一）

**目标**：按听力曲线提升对应频段的响度。

| 功能点 | 说明 |
| --- | --- |
| 参数来源 | 当前档案的左右耳补偿参数（EQ 增益 + 前置增益 + 压缩/限幅） |
| 左右耳独立 | 左声道走左耳参数，右声道走右耳参数 |
| Demo 试听 | 内置测试音（扫频/人声样本）+ 原音↔增强即时 AB 切换 |
| 本地文件处理 | 拖入音频/视频，导出处理后的文件（视频先仅处理音轨或输出音频） |
| 立即生效 | 参数调整后无需重启 |

**验收标准**
- AB 切换无爆音、无明显延迟切换感；
- 处理后的文件可正常播放，波形不削波；
- 左右耳参数不同时，能听出差异。

### 4.5 M5 听力增强（频率重映射，方案二，进阶）

**目标**：把用户听不到的高频/低频搬移到可听的中频区。

| 功能点 | 说明 |
| --- | --- |
| 映射策略 | 线性频率压缩 / 分段搬移 / 非线性压缩，可切换 |
| 参数 | 起始频率、压缩比、目标频带上限（沿用 `shiftHz / fmin / fmax`） |
| 离线处理 | 先做离线（STFT → 重排 → iSTFT），验证效果 |
| 实时处理 | 后期接入虚拟声卡链路 |

**验收标准**
- 复合纯音测试中，高频峰可观测到下移；
- 输出无严重相位失真/音乐噪声；
- 与方案一可组合或独立选择。

> 技术路线论证见《频谱重映射_技术路线论证.md》：**确定性 DSP 实现，不用生成式大模型**。

### 4.6 M6 视频字幕生成

| 功能点 | 说明 |
| --- | --- |
| 批量上传 | 一次可选多个视频/音频文件，排队处理 |
| 本地 ASR | 模型在本机运行，音频不出本机 |
| 输出 | SRT / VTT 字幕，可选择嵌入视频或外挂 |
| 进度与失败重试 | 显示每个文件的状态、进度、失败原因 |
| 硬件适配 | CPU 可用（慢但能跑），有 GPU 时加速 |

**验收标准**：10 分钟中文视频在普通笔记本上 ≤ 5 分钟生成可用字幕（base 模型）。

### 4.7 M7 虚拟声卡实时增强（核心价值）

| 功能点 | 说明 |
| --- | --- |
| 系统级接管 | 用户把默认播放设备设为虚拟声卡，程序捕获后处理，再输出到真实耳机/音箱 |
| 实时链路 | 捕获 → 双耳 DSP → 输出，端到端延迟目标 < 30 ms |
| 一键启停 | 托盘/主界面开关，随时可关闭恢复原声 |
| 设备选择 | 可选输入（虚拟声卡）与输出（真实设备） |
| 降级保护 | 处理失败时自动直通，避免用户突然听不到声音 |

**验收标准**
- 观看视频时音画不同步感可接受（延迟 < 30 ms）；
- 连续运行 1 小时无爆音、无内存增长；
- 关闭开关后声音立即恢复正常。

### 4.8 M8 账号与同步（可选）+ 隐私同意

| 功能点 | 说明 |
| --- | --- |
| 游客模式 | **默认形态**。不登录、不联网，全部功能可用（除深度分析） |
| 可选注册 | 用户主动选择注册/登录，用于跨设备同步与深度分析 |
| 同步内容 | 仅同步**听力曲线与派生参数**，不同步原始音频、不同步使用日志明细 |
| 隐私协议 | 登录后首次进入展示，需**明确勾选同意**才会上传；可随时撤回 |
| 最小必要 | 服务端不收集设备标识、不收集音频、不收集精确位置 |
| 匿名化 | 统计分析使用随机化 ID，与账号解绑；仅聚合到人群层面 |
| 数据权利 | 支持导出、删除服务端数据；撤回同意后停止上传并删除已有数据 |

**验收标准**
- 未同意隐私协议时，服务端**收不到任何用户数据**（可用抓包验证）；
- 撤回同意后，服务端数据被删除或匿名化；
- 游客与登录用户在本地功能上完全一致。

### 4.9 M9 深度分析与建议（登录专享）

| 功能点 | 说明 |
| --- | --- |
| 输入 | 双耳曲线、PTA、分级、使用场景（可选） |
| 处理 | 服务端调用外部大模型 API，结合听力学知识库生成建议 |
| 输出 | 通俗解读 + 补偿建议 + 就医提示（"建议到听力中心做标准测听"） |
| 边界 | **不得输出诊断结论**；固定免责声明；敏感内容由知识库约束 |

**验收标准**：建议内容不含诊断性表述；同输入多次调用结果稳定可接受；响应时间 < 10 s。

## 6. 技术选型论证

### 6.1 桌面外壳：Tauri 2 vs Electron

| 维度 | Tauri 2 | Electron |
| --- | --- | --- |
| 安装包体积 | 8–15 MB | 80–150 MB |
| 常驻内存 | 50–90 MB | 150–250 MB |
| 原生音频能力 | Rust 直接调 WASAPI/cpal，同进程低延迟 | 需 native 模块（naudiodon 等）或另起进程 |
| 现有 React 代码 | 直接复用 | 直接复用 |
| WebView | 系统 WebView2 | 自带 Chromium |
| 学习成本 | 需少量 Rust | 纯 JS |
| 生态成熟度 | 中 | 高 |

**结论：选 Tauri 2。** 决定性理由不是体积，而是 **Rust 音频后端**——你的实时 DSP 和虚拟声卡捕获本来就要写原生代码，Tauri 让它在同一进程里完成，Electron 则要额外引一层 native 模块或独立进程。

> 风险：Rust 学习曲线。对策：音频层先用最小实现（`cpal` 采音 + 固定参数 EQ），不追求架构优雅。

### 6.2 本地存储：SQLite 及访问方式

选 SQLite 是明确结论（对比见上一轮实测：Postgres 55 MB 内存 + 419 MB 镜像，SQLite 1–3 MB 单文件）。

访问方式三选一：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| `@tauri-apps/plugin-sql` | 官方插件，TS 里写 SQL | 零 Rust 代码，最快上手 | 无类型安全，手写 SQL |
| Rust 层 `rusqlite` + `invoke` 命令 | 数据层在 Rust | 类型安全、性能好 | 领域逻辑要跨语言 |
| Drizzle ORM + sql.js(WASM) | TS ORM | 类型安全 | WASM 性能一般，持久化要自己接 |

**结论：MVP 用 `tauri-plugin-sql` + 手写 SQL + 迁移脚本**；如果后期数据访问变复杂，再上 Rust 层。理由：**先把产品跑起来，类型安全可以后补**。

> 注意：Prisma **不能**在 Tauri 里运行（依赖 Node 运行时），桌面端必须换数据访问方式。

### 6.3 音频 DSP：Rust

| 方案 | 实时性 | 与桌面壳集成 | 结论 |
| --- | --- | --- | --- |
| Rust（`cpal` + `biquad` + `rustfft`） | 优秀 | 同进程 | ✅ 推荐 |
| C++ | 优秀 | 需 FFI | 备选 |
| Python | 差（GIL/GC 抖动） | 需子进程 | 只用于离线批处理 |

**结论：实时链路用 Rust**；离线批量处理（如整段视频重映射）可以先用 Rust 或 Python，不追求统一。

### 6.4 字幕 ASR：模型放哪、怎么跑

| 方案 | 体积成本 | 集成难度 | 结论 |
| --- | --- | --- | --- |
| `whisper-rs`（Rust 绑定 whisper.cpp） | 二进制 +5–10 MB，模型 base 150 MB / small 500 MB | 中 | ✅ **桌面端首选**，单文件分发、无 Python |
| whisper.cpp CLI 作为 sidecar | +20 MB | 低 | 备选，进程间通信稍麻烦 |
| `faster-whisper`（Python） | 打包 Python 环境 300 MB+ | 高 | 只在服务端用 |
| 云 ASR API | 0 | 低 | 违反"音频不出本机"，仅作可选

**结论：桌面端用 `whisper-rs`，模型按需下载**（首次使用提示下载，可离线导入）。

### 6.5 服务端：Next.js vs FastAPI vs Supabase

先明确服务端只做四件事：**账号、档案同步、使用统计（匿名）、听力建议（调外部 LLM）**。它**不碰音频**。

| 维度 | Next.js（现有） | FastAPI | Supabase |
| --- | --- | --- | --- |
| 与桌面端共享领域逻辑 | ✅ 听力学计算可直接共用 TS 代码 | ❌ 需用 Python 重写一遍 | ⚠️ Edge Function 可用 TS，但受限 |
| 现有代码复用 | ✅ 已有 10 个接口、认证、双耳档案 | ❌ 全部重写 | ❌ 全部重写 |
| 账号/数据库/存储 | 自建（Prisma + Postgres） | 自建 | ✅ 开箱即用 |
| 向量检索（知识库） | 需装 pgvector | 需装 pgvector | ✅ 内置 |
| 国内访问稳定性 | ✅ 可自建/国内云 | ✅ | ⚠️ 官方云在境外，访问不稳 |
| 健康数据合规 | ✅ 数据可留境内 | ✅ | ⚠️ 跨境传输需评估 |
| 单人开发成本 | 低（已跑通） | 中 | 低（但学习新范式） |

**结论：MVP 保留 Next.js + Prisma + Postgres。**

理由：
1. **已有可用代码**，重构桌面端已经够多了，服务端不该再推翻；
2. **领域逻辑共用**：听力学计算（`audiogram.ts`）是纯函数，桌面端和服务端都能用，这是 Next.js 独有的优势；
3. **数据合规**：听力曲线属于敏感健康数据，自建在国内服务器最稳妥；Supabase 官方云在境外，跨境传输需要额外评估；
4. FastAPI 的优势（音频/AI 生态）在这里用不上——服务端不跑模型，只调外部 API。

**Supabase 的合理用法**：作为「托管 Postgres + Auth」的替换项，等 MVP 稳定后再评估；若要用，优先自托管（Supabase self-hosting）或选择境内区域，避免跨境。

### 6.6 系统级音频接管方案（原"虚拟声卡方案"）

#### 6.6.1 先看懂"变声器"到底做了什么

变声器类工具的链路是：**虚拟设备 → 捕获 → DSP → 输出到真实设备**。这条链路的后半段（捕获、DSP、输出）和你要做的完全一样；差别只在**前半段"虚拟设备"从哪来**，而这有三种来源：

| 来源 | 谁在用 | 代价 |
| --- | --- | --- |
| 自带签名虚拟驱动 | Voicemod、MorphVOX 等商业软件 | 公司持有 EV 证书 + 微软签名，驱动随安装包分发 |
| 现成虚拟声卡（VB-CABLE 等） | 大量小工具、直播软件 | 免费但闭源；转发需查许可 |
| APO / VST 宿主 | Equalizer APO 等 | 不需要虚拟设备，但要写 COM 或 VST |

**所以"路线相似"成立，"成本相似"不成立**：变声器不是绕过驱动，而是把驱动签名这件事做完了。好消息是——**你不写驱动也能做到**，因为现成方案已经把"设备"这一环提供了。

#### 6.6.2 五条路线对比

| 路线 | 需要驱动 | 覆盖范围 | 能否做频率重映射 | 开发量 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **A. Equalizer APO 配置文件** | 否（用户装 APO） | 整机所有声音 | ❌ 只能做线性滤波（EQ/增益） | **1–2 天** | ✅ v0.2 立刻见效 |
| **B. Equalizer APO + 自研 VST2 插件** | 否 | 整机所有声音 | ✅ | 2–3 周（C++/JUCE） | ⚠️ 可行但有坑，见 6.6.3 |
| **C. VB-CABLE + 自研 Rust 应用** | 现成免费驱动 | 整机（切换默认设备） | ✅ | 2–3 周 | ✅ v0.3 主路线 |
| **D. 进程环回（Win11）** | 否 | 单个应用/进程树 | ✅ | 2 周 | 🔶 轻量备选 |
| **E. 自研 APO（COM）** | 否 | 整机 | ✅ | 1–2 月 | 🔭 v1.0 目标 |
| F. 自研虚拟驱动 | 需 EV + 微软签名 | 整机 | ✅ | 数月 | ❌ 不建议 |

补充说明：

- **WASAPI 环回（默认设备）不可行**：它捕获的是设备最终混音，原声仍会播放 → 双重声音；静音设备又会连捕获一起静音。
- **Scream**（MS-PL 开源）是网络组播型虚拟声卡，多一跳网络抖动，不适合实时本地链路。
- **SynchronousAudioRouter**（GPL-3.0）开源但项目老旧、维护弱，仅作备选评估。

#### 6.6.3 两条"零驱动"捷径（值得先做）

**捷径 1：生成 Equalizer APO 配置（覆盖方案一）**

[Equalizer APO](https://sourceforge.net/projects/equalizerapo/) 是实现系统级 EQ 的成熟开源方案，配置语法在[官方文档](https://sourceforge.net/p/equalizerapo/wiki/Configuration%20reference/)中有完整说明。我们的应用只需**根据听力档案生成一段配置文本**：

```
Device: <耳机设备名>
Preamp: -6 dB
Channel: L
Filter 1: ON PK Fc 1000 Hz Gain 5.0 dB Q 1.00
Filter 2: ON PK Fc 4000 Hz Gain 12.0 dB Q 1.00
Channel: R
Filter 1: ON PK Fc 1000 Hz Gain 3.0 dB Q 1.00
...
```

写入 Equalizer APO 的配置目录后，**整机所有声音立刻按双耳参数处理**，不需要虚拟设备、不需要写任何驱动。这是 v0.2 性价比最高的一步（1–2 天工作量，直接拿到"系统级"体验）。

局限：配置语法只支持**线性滤波**（Peaking/Shelf/GraphicEQ/Convolution/IIR），**做不了频率重映射**（那是时变处理），只能覆盖方案一。

**捷径 2：进程环回（Win11，逐应用）**

微软提供 [`AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`](https://learn.microsoft.com/zh-cn/Windows/Win32/api/audioclientactivationparams/ne-audioclientactivationparams-audioclient_activation_type)，可捕获**指定进程及其子进程**的音频；配合 `ISimpleAudioVolume` 静音原会话，就不会有双重声音。OBS 的「应用音频捕获」用的就是这套（[参考实现](https://github.com/eoNaho/win-capture-audio)）。

⚠️ 官方标注**最低支持 Windows 10 build 20348**，而消费版 Windows 10 最高只到 19045 —— 实际等于**仅 Windows 11 可用**（Win10 2004+ 是否可用需实测，OBS 社区有争议）。

适用场景：只想增强某个播放器/会议软件。局限：不是"整机所有声音"。

**关于 VST2（路线 B 的坑，先说清）**

社区已验证 Equalizer APO 支持 `VSTPlugin: Library "C:\path\to\plugin.dll"`（[讨论帖](https://sourceforge.net/p/equalizerapo/discussion/general/thread/fc7e51287e/)），但：

1. 只支持 **VST2**，不支持 VST3；
2. 官方配置文档**未列出**该命令，属非正式特性，版本升级可能失效；
3. **无法在配置里设置插件参数**（chunk 数据格式不标准）→ 插件必须自己从 JSON/注册表读参数；
4. VST2 SDK 已被 Steinberg 停止分发，新项目要处理许可问题。

因此：路线 B 能做，但**不作为主线**；除非你确实想要"单一直觉方案 + 免切设备"的体验。

#### 6.6.4 推荐的分阶段路径

| 阶段 | 采用路线 | 交付效果 | 工作量 |
| --- | --- | --- | --- |
| v0.2 | **A. Equalizer APO 配置** | 整机所有声音获得增益补偿（方案一），立即可演示 | 1–2 天 |
| v0.3 | **C. VB-CABLE + Rust** | 整机所有声音，方案一 + 方案二完整可控 | 2–3 周 |
| v1.0 | **E. 自研 APO** | 免虚拟设备、免切换、体验最优 | 1–2 月 |
| 可选 | **D. 进程环回** | Win11 上"只增强某个应用"的轻量模式 | 2 周 |

这个路径的好处：**每一步都有可演示的成果**，且 v0.2 只花两天就能拿到"系统级"效果，能极大缓解"做了很久还看不到效果"的焦虑。

> **2026-11-06 决策（修订）：不做虚拟声卡，也不走 Equalizer APO 配置路线，目标直接定在「自研 APO + Rust DSP」。**
>
> 需求是「**改一次系统输出，所有应用自动生效，不需要逐个应用配置**」。逐条对照：
>
> | 路线 | 是否符合需求 | 结论 |
> | --- | --- | --- |
> | 虚拟声卡（VB-CABLE） | ❌ 要用户切默认播放设备；固定输出设备的应用会绕过 | 不采用 |
> | 进程环回（Win11） | ❌ 本质上就是逐进程配置 | 不采用 |
> | Equalizer APO 配置 | ✅ 全局生效，但 ❌ 只能线性滤波，做不了频率重映射 | 仅保留为只读导出 |
> | **自研 APO（SFX/EFX）** | ✅ 注册到输出端点，该端点上的所有应用都经过它；✅ APO 回调内可写任意 DSP（含 STFT） | **目标方案** |
>
> 关于「APO 不能做频率重映射」的澄清：这**不是** APO 架构的限制。APO 的 `APOProcess` 是普通的实时音频回调，STFT 重映射完全可行；受限的只是 Equalizer APO 自己的配置语法（只支持线性滤波）。
>
> 代价与风险（必须写进论文的风险分析）：C++ COM 组件开发、按端点注册、`audiodg.exe` 内的实时约束（不得阻塞/分配内存）、崩溃会导致整机音频失效、连续失败 10 次会被系统自动禁用效果、受保护内容（DRM）要求 APO 已签名。
>
> 过渡方案：若 APO 首版未就绪，可用 **WASAPI 环回捕获 + 逐会话静音** 做临时演示（无需驱动，但有延迟与竞态风险），不作为产品路线。

#### 6.6.5 结论

- 不需要写驱动，也不需要买签名证书——那是商业变声器的成本项；
- **自研 APO 是唯一同时满足「全局生效 + 不切设备 + 可做频率重映射」的路线**（COM 组件 + 按端点注册）；
- APO 的注册与配置由我们的桌面端完成，音频数据全程不经过我们的进程；
- Equalizer APO 配置导出保留为只读辅助（用户想用可自行安装），不作为主路径；

                                    ▼

**关键原则**
1. 音频与原始数据**永不出本机**；
2. 服务端只做"账号 + 曲线 + 建议"，做减法；
3. 游客模式下服务端**完全不参与**。

## 8. 数据设计

### 8.1 本地 SQLite（桌面端）

```sql
-- 听力档案（多份，可切换）
CREATE TABLE profiles (
  id            TEXT PRIMARY KEY,
  name          TEXT NOT NULL,
  left_config   TEXT,          -- JSON: EarCompensation | null
  right_config  TEXT,          -- JSON: EarCompensation | null
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL
);

-- 测听会话
CREATE TABLE test_sessions (
  id          TEXT PRIMARY KEY,
  ear         TEXT NOT NULL CHECK (ear IN ('LEFT','RIGHT')),
  device_note TEXT,
  results     TEXT NOT NULL,   -- JSON: [{frequency, level, heard}]
  threshold   REAL,
  started_at  TEXT NOT NULL,
  finished_at TEXT
);

-- 处理任务（字幕 / 增强）
CREATE TABLE jobs (
  id          TEXT PRIMARY KEY,
  type        TEXT NOT NULL,   -- 'subtitle' | 'enhance'
  input_path  TEXT NOT NULL,
  output_path TEXT,
  status      TEXT NOT NULL,   -- queued|running|success|failed
  progress    INTEGER DEFAULT 0,
  error       TEXT,
  created_at  TEXT NOT NULL
);

-- 设置与同意状态
CREATE TABLE settings (key TEXT PRIMARY KEY, value TEXT NOT NULL);
CREATE TABLE consents (version TEXT PRIMARY KEY, accepted_at TEXT, revoked_at TEXT);

-- 同步状态
CREATE TABLE sync_state (key TEXT PRIMARY KEY, value TEXT NOT NULL);
```

### 8.2 服务端 Postgres（沿用现有 Prisma 模型，做减法）

- `users`：账号
- `profiles`：每用户每耳一份曲线与派生参数（**不存原始音频**）
- `consents`：隐私协议同意/撤回记录
- `usage_events`：匿名化使用统计（随机化 ID，与账号解绑）
- `advice_requests`：建议生成记录（可选保留，用于质量评估）

### 8.3 同步策略

- 只同步 `profiles`（曲线 + 参数）；
- 冲突处理：以 `updated_at` 较新者为准；
- 用户可关闭同步；关闭后本地改动不上传。

### 9.2 MVP 范围（只做这些）

### 9.3 阶段计划

| 阶段 | 周期 | 交付物 | 验收 |
| --- | --- | --- | --- |
| **P0 骨架** | 1 周 | Tauri 项目跑起来；React 页面能加载；SQLite 可读写；`pnpm dev` 浏览器预览照常 | 安装包能启动，数据库文件生成 |

| **P3 增强** | 1.5 周 | Demo 试听（扫频 + 内置样本）+ 本地音频/视频拖入处理导出 | AB 无爆音；输出不削波 |
| **P4 打包** | 1 周 | Windows 安装包、图标、版本号、基础设置页 | 干净机器安装即用 |

**合计约 5.5 周**，预留 1 周缓冲 → **6.5 周**。

### 9.4 后续版本

| 版本 | 内容 | 依赖 |
| --- | --- | --- |
| v0.2 | **自研 APO 首版**（C++ COM 薄壳 + Rust DSP cdylib）：注册到默认输出端点，方案一全机型生效；视频字幕（whisper-rs + 批量队列） | P4 完成；需先完成 APO 回调实时性验证 |
| v0.3 | 频率重映射完整实现（STFT 分段搬移）+ 双耳独立参数 + 直通降级（APO 内异常自动 bypass） | v0.2 APO 链路稳定 |
| v0.4 | 账号 + 同步 + 隐私同意 + 深度分析 | 服务端改造（同步与同意已完成） |
| v1.0 | 多端点批量注册、受保护内容签名、自动更新、安装包签名 | 全部 |

> 2026-11-06 修订：取消 VB-CABLE 与 Equalizer APO 配置作为产品路线，统一走自研 APO，理由见 6.6.4。

### 9.5 为什么这个顺序

1. **先能装**：不能安装的产品等于没做；
2. **先离线**：离线可用是所有后续功能的地基，也符合隐私定位；
3. **先测听再增强**：增强依赖测听产出的参数，且测听已跑通，迁移成本最低；
4. **字幕放 v0.2**：它是独立模块，不阻塞核心链路，且模型体积大，需要单独设计下载策略；
5. **虚拟声卡放 v0.3**：技术风险最高（实时性、驱动、兼容），必须放在有稳定基础之后。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| Rust 学习成本导致进度拖延 | 高 | 音频层先用最小实现；DSP 算法先在 TS 原型验证（已有），再移植 |
