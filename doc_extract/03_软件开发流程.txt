[Normal] 一、项目概述
[Normal] 1.1 项目定位
[Normal] 本项目面向听障与重听人群（重点为青少年与年轻成年人），构建一个 Web 端辅助平台，把“可读的字幕”“可测的听力”“可调的音频”三类能力整合到同一条处理链路上：用户上传视频后，系统自动生成带时间信息的字幕；用户通过纯音自测形成个体化听力配置；系统依据该配置对音轨做实验性频谱重映射，生成增强音轨供在线对比播放。项目在软件工程层面的核心工作是语音识别、Web 音频处理与业务系统的模块化集成。
[Normal] 需要界定的边界：听力自测定位为辅助筛查与个性化参数采集，不做医疗诊断；频谱重映射定位为实验性音频处理策略，其映射规则与参数由本项目自行设计，不等同于临床助听器的标准频率降低算法。

[Normal] 1.3 技术架构与分层
[Normal] 总体架构采用“模块化单体业务后端 + AI 微服务”，在控制系统复杂度的同时保留 AI 能力独立扩展的空间。四层职责与开发归属如下表，每层对应独立代码仓库目录、独立构建产物和独立部署单元，层与层之间只通过已定义的接口契约通信。
<<TABLE 6 rows x 5 cols>>
| 层次 | 技术选型 | 职责 | 开发负责人 | 交付形态 |
| 前端应用层 | React 18 + TypeScript + Vite + Ant Design + Video.js + Web Audio API + ECharts | 页面交互、视频播放、纯音播放与反馈采集、字幕编辑、参数调节与可视化 | 本人 | 静态构建产物 |
| 业务后端层 | NextJS + TypeScript + Prisma + PostgreSQL + Redis + BullMQ + JWT | 用户与权限、视频与字幕元数据、听力档案、任务编排、REST 接口与进度推送 | 本人 | Node 服务镜像 |
| AI 微服务层 | FastAPI + Python + faster-whisper / WhisperX + ffmpeg + librosa + torchaudio | 语音识别与字幕生成、音频解码与频谱重映射、增强音轨合成 | 本人 | Python 服务镜像 |
| 存储与通信层 | MinIO / S3、PostgreSQL、Redis；REST + SSE / WebSocket | 文件与音视频对象存储、结构化数据持久化、任务队列与实时进度通道 | 本人 | 基础设施编排 |
| 部署与运维层 | Docker Compose + Nginx + GitHub Actions | 一键拉起全栈环境、反向代理与静态资源、镜像构建与自动部署 | 本人 | compose 编排文件 |

<<END TABLE>>
[Normal] 1.4 核心数据流
[Normal] 全流程以一次“上传—处理—增强—播放—记录”为主线，任一环节失败均可从任务记录中定位与重跑：
<<TABLE 8 rows x 6 cols>>
| 序号 | 处理环节 | 输入 | 处理动作 | 输出 | 承载模块 |
| 1 | 视频上传 | 用户视频文件 | 分片上传、校验格式与大小、生成资源 ID | 原始视频对象、资源记录 | M3 |
| 2 | 提取音频 | 原始视频对象 | ffmpeg 解码为 16kHz 单声道 WAV 并入库 | 标准音频轨 | M3 / M5 |
| 3 | AI 字幕生成 | 标准音频轨 | VAD 切分、语音识别、时间对齐、生成 SRT/VTT 与分段数据 | 字幕文件、分段与置信度 | M4 |
| 4 | 用户听力配置 | 自测反馈数据 | 分频纯音播放与反馈采集、计算频率感知曲线与可听区间 | 个性化听力配置 JSON | M2 |
| 5 | 频谱重映射 | 音频轨 + 听力配置 | STFT 分析、频率压缩/搬移、按配置计算映射参数 | 重映射音频数据 | M5 |
| 6 | 生成增强音轨 | 重映射音频数据 | iSTFT 重建、响度归一化、编码为可播放音轨 | 增强音轨对象 | M5 |
| 7 | 播放与结果记录 | 原音轨 / 增强音轨 / 字幕 | AB 对比播放、主观评价量表、写入实验记录 | 实验数据集、统计图表 | M2 / M6 |

<<END TABLE>>
[Normal] 二、总体开发流程与阶段划分
[Normal] 按开题报告 16 周进度，把开发过程组织为 8 个阶段（P0—P7）。阶段之间存在明确的门禁：上一阶段的验收标准未全部满足时，不进入下一阶段的功能开发，只允许进行缺陷修复与文档补充。第 10—14 周为联调、测试、实验与部署并行推进的收敛期，第 15—16 周回到论文与答辩。

[Normal] 5.2 缺陷处理与阶段门禁
[Normal] 缺陷分级：严重（主链路不可用或数据损坏）→ 立即修复；一般（功能可用但有偏差）→ 当期修复；轻微（体验与文案）→ 排期修复。
[Normal] 缺陷闭环：登记 → 复现步骤 → 定位原因 → 修复 → 回归验证 → 关闭，全部记录在册，作为测试章节的材料。
[Normal] 阶段门禁：阶段出口的三项条件同时满足才进入下一阶段 —— 交付物齐备、完成标准逐条核对通过、无未处置的严重缺陷。
[Normal] 代码门禁：提交前通过静态检查与本地测试；合并到主分支前完成一次端到端冒烟。
