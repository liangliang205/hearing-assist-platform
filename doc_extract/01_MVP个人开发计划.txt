[Normal] 一、总体思路
[Normal] 一个人做项目，最大的敌人不是技术难度，而是范围失控和“什么都想做”。因此本计划把开题报告里的 7 个模块重新切分为 MVP 与后续版本：MVP 只保留让核心链路成立的必需功能，并且刻意选择“工程量小、风险低”的实现方式，把有限的时间留给真正需要验证的两件事——AI 字幕能不能用、频谱增强能不能听出效果。
[Normal] 1.1 四条个人开发原则
[Normal] · 垂直切片：每周交付一条“能点能看”的端到端功能，不做完整个后端再做前端。先跑通，再做好。
[Normal] · 工程量优先于技术先进性：能用 Web Audio API 原生节点实现的音频效果，就不引入 librosa 重写一整套离线处理；能用轮询拿到任务进度，就不做 WebSocket。
[Normal] · 每周必须有可演示产物：周五/周日各留一次“打开浏览器走一遍”的验证，跑不通就不算完成。
[Normal] · 范围可砍，质量不砍：时间不够就砍功能（走“可延后”清单），不通过降低正确性、稳定性来换进度。
[Normal] 1.2 五分钟读懂本计划
[Normal] 第 1—2 周打地基并先做一次技术预研（把最大的坑提前踩掉）；第 3—5 周完成“上传视频 → 出字幕 → 播放”这条主线；第 6—8 周完成“听力自测 → 个性化增强 → 原音/增强对比”，至此 MVP 成立；第 9—12 周做健壮性、部署与整体打磨，形成可演示、可验收的成果。
[Normal] 二、MVP 范围定义
[Normal] 2.1 核心用户旅程（MVP 只做这一条）
[Normal] 注册/登录 → 完成一次听力自测并保存听力配置 → 上传一个视频 → 系统自动生成字幕 → 播放时挂载字幕 → 打开“语音增强”并按自测结果一键补偿 → 在原音与增强之间切换对比。旅程之外的任何功能，一律不属于 MVP。

[Normal] 2.4 技术简化决策（MVP 专用）
[Normal] 下面这些替换是为了让一个人能在 12 周内交付，并且全部保留后续升级路径；换回来的时间直接投到字幕质量与增强效果这两个真正要验证的点上。
<<TABLE 9 rows x 4 cols>>
| 环节 | 原计划（开题报告） | MVP 采用 | 换回来的收益 / 升级路径 |
| 音频处理 | librosa + torchaudio + STFT 离线频谱重映射 | Web Audio API 原生节点（EQ/压缩/滤波）实时处理 | 省掉整套离线链路与依赖；v1.1 再补离线重映射做对比 |
| 任务进度 | SSE / WebSocket 实时推送 | 前端每 2 秒轮询任务状态接口 | 省掉事件通道与断线重连；接口结构不变，后续可平滑替换 |
| 文件存储 | MinIO / S3 对象存储 | 本地磁盘 + 静态资源路由 | 省掉一个中间件；存储层做接口抽象，后续换 S3 只改一处 |
| 实时进度条 | WebSocket 推送百分比 | 阶段化状态（排队/处理中/完成/失败） | 视觉更简单但信息足够，减少前后端联调成本 |
| 前端播放器 | Video.js + 自定义字幕轨道 + 音频切换 | HTML5 video + 原生 track 标签 + 双音轨切换 | 省掉播放器定制；字幕与音频切换逻辑不变 |
| 数据库 | PostgreSQL 全量设计 | 模型按 PostgreSQL 设计，开发期可用 SQLite 提速 | 减少本地环境负担；字段与迁移保持兼容 |
| 测试策略 | 完整单元/接口/集成测试体系 | 只测高风险逻辑：鉴权、上传校验、任务状态、参数计算 | 用 20% 的测试覆盖 80% 的回归风险 |
| 调度与队列 | BullMQ + Redis 完整任务编排 | BullMQ 单队列 + 单 worker（AI 服务轮询消费） | 减少并发与依赖管理；后续按需加 worker 即可扩展 |

<<END TABLE>>

| 第 6 周 / 16—20h | 增强线 | 听力自测可用 | Web Audio API 生成 5 个频点测试音（含播放前音量校准与设备提示）；简化自测流程（是/否反馈）；计算结果生成听力配置 JSON 并保存到档案；简单折线展示；加免责说明 | 能完整走完自测并看到结果曲线，配置已保存 / 验收：重复自测结果基本一致；配置可被后续页面读取 |
| 第 7 周 / 18—22h | 增强线 | 按听力配置做语音增强（关键路径） | Web Audio 链路：三段 EQ + 高频补偿 + 动态范围压缩；由听力配置计算各频段增益；强度滑块（0—100%）与实时生效；方案不理想时启用离线重映射备选方案 | 播放时能明显听出增强效果，参数随滑块变化 / 验收：听感有可辨识改善；无爆音、无卡顿、无爆音式削波 |
| 第 8 周 / 16—20h | 增强线 | 原音/增强对比（MVP 成立） | 双音轨切换（同一时间轴无缝切换）；增强开关与字幕共存；记录使用的参数；MVP 全链路走查并修补断点 | 一键切换原音/增强，字幕保持同步；完整演示一遍 / 验收：MVP 定义中的那条旅程可一次性走通 |
| 第 9 周 / 14—18h | 打磨 | 健壮性：让系统不崩 | 异常处理：超大文件、损坏文件、转码失败、模型超时、网络中断；任务重试；加载态与空态；长视频（30 分钟以上）跑通并记录资源占用 | 异常场景下给出明确提示且系统可恢复 / 验收：故意制造 5 类故障，系统均不白屏、不丢数据 |
| 第 10 周 / 14—18h | 打磨 | 端到端走查 + 缺陷收敛 | 按用例清单完整走查 7 个模块的 MVP 功能；修复发现的问题；统一文案与视觉细节；移动端基本可用性检查 | 缺陷清单收敛，主链路稳定可反复演示 / 验收：同一演示流程连续 3 次无失败 |

[Normal] 四、单人开发的工作方式
[Normal] 4.1 时间怎么排
<<TABLE 5 rows x 4 cols>>

| 周一至周五 晚间 | 1.5h/天 | 写单个小功能、修 bug、写接口与页面 | 不要在这段时间做技术预研或架构重构（容易被切断思路） |

| 周日 晚间 | 0.5h | 复盘：本周演示是否通过、下周唯一目标是什么 | 不要跳过复盘（这是单人项目最容易失控的环节） |

<<END TABLE>>
[Normal] 现实预期：计划按 20 小时/周制定，但实际生活中每周会有 30%—40% 的损耗（课程、考试、状态）。因此第 4、7 周这类关键周建议安排在没有考试的时段；若某周只完成 60%，优先把该周的核心目标补齐，其余任务顺延，不要并行推进两周的任务。
[Normal] 4.2 每周固定动作
[Normal] · 周日定计划：写下下周唯一目标 + 不超过 5 个具体任务（写进一个 TODO.md 或用看板工具，不要用脑子记）。
[Normal] · 每日一次提交：提交信息用“类型(范围): 说明”（feat/fix/docs/refactor），当天的进度当天入库。
[Normal] · 周中做一次冒烟：周三晚用 10 分钟把已完成功能点一遍，避免问题堆到周末才发现。
[Normal] · 周五留 30 分钟写周报：完成了什么、卡在哪、下周准备怎么做，这份记录后面直接变成论文的过程材料。
[Normal] · 每周结束时保证仓库可运行：卡住的功能放 feature 分支或加开关，不让主分支处于半坏状态。

[Normal] 4.4 提交前自检清单（30 秒版）
[Normal] · 功能：新写的路径能跑通；没把旧功能弄坏（点一遍相关页面）。
[Normal] · 数据：不再产生孤儿记录与残留文件；失败任务有状态可查。
[Normal] · 体验：加载中有提示；出错有可读的中文提示，不是白屏或英文堆栈。
[Normal] · 仓库：没有提交密钥、测试视频、模型文件等大文件；README 与实际启动方式一致。
[Normal] 五、先做技术预研：把坑提前踩掉
[Normal] 单人项目最怕“做到第 4 周才发现关键技术在本地跑不动”。因此第 1 周安排一次 Spike（预研），只写验证代码、不写产品代码，每项限时并记录结论，结论直接决定 MVP 的降级方案。
<<TABLE 6 rows x 4 cols>>
| 预研项 | 验证内容 | 判断标准 | 不通过时的降级方案 |
| Whisper 字幕 | faster-whisper 在本人机器上跑 10 分钟中文音频，测耗时、内存、显存占用与字幕可读性 | CPU 上 10 分钟音频 ≤ 8 分钟处理完且字幕可用 | 换小模型/分段处理；或把长视频改为短片段演示 |
| ffmpeg 转码 | 常见格式转 MP4 与抽音频的耗时与成功率 | 5 分钟视频 ≤ 60 秒完成 | 限制上传格式与时长，前端给出时长上限提示 |
| 浏览器音频增强 | Web Audio 链路（EQ+压缩+滤波）在 Chrome 上实时播放是否稳定、有无爆音 | 连续播放 10 分钟不卡顿、无削波 | 改用服务端离线重映射（预留 2 天） |
| 自测音频播放 | 测试音频率准确性与音量控制在不同设备上是否可用 | 能听清且频率可信（可用手机 App 粗校） | 改为固定增益的简化测试，明确标注精度限制 |
| AI 服务通信 | Node 与 FastAPI 之间的任务派发与状态回传 | 任务不丢失、状态与实际处理一致 | 改为同步调用 + 超时控制，牺牲异步性换确定性 |

<<END TABLE>>

[Normal] 六、MVP 验收标准与止损线
[Normal] 6.1 验收标准（第 12 周末逐条核对）
<<TABLE 9 rows x 3 cols>>
| 编号 | 验收项 | 通过标准 |
| A1 | 核心旅程完整 | 新用户注册 → 听力自测 → 上传视频 → 出字幕 → 播放带字幕 → 开启增强 → 原音/增强对比，全程无需人工干预 |
| A2 | 字幕质量可用 | 10 分钟中文视频字幕可读，时间轴抽检无明显漂移，给出抽检记录 |
| A3 | 增强可辨识 | 能在原音与增强之间稳定切换，听感有可描述差异，无爆音与卡顿 |
| A4 | 自测可复现 | 同一环境下重复自测结果基本一致，差异有记录与解释 |
| A5 | 系统健壮 | 5 类典型故障（超大文件、损坏文件、模型超时、网络中断、任务失败）均有明确提示且可恢复 |
| A6 | 可部署可复现 | 干净机器按 README 在 1 小时内完成部署并访问全部 MVP 功能 |
| A7 | 论文材料就绪 | 系统截图、处理耗时数据、字幕抽检数据、增强主观评价数据成套 |
| A8 | 范围受控 | P2/P3 清单未混入本期实现，超出范围的变更均有记录 |

[Normal] MVP 不是终点，而是把论文的“系统实现”章节立起来的最小骨架。后续版本按“先补论文需要的数据，再补功能完整性”的顺序推进，避免为了堆功能而牺牲论文材料的完整性。
<<TABLE 5 rows x 4 cols>>

| v1.1 | 第 13—14 周 | 按自测结果的离线频谱重映射（STFT + 频率压/搬移，librosa/torchaudio），与浏览器增强做对比；任务失败重试与进度细化 | 体现开题报告中的核心算法工作，支撑“频谱重映射”研究内容 |

| v1.3（可选） | 第 16 周 | 说话人分离、字幕质量自动评估、部署自动化 | 作为未来工作与扩展性讨论的素材 |

[Normal] 八、主要风险与个人应对
<<TABLE 9 rows x 3 cols>>
| 风险 | 征兆 | 个人应对（可执行动作） |
